# Deployment

Continuous delivery is defined by [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml).
A push to `main` deploys **only after the `CI` workflow finishes successfully** (`workflow_run` trigger).
Images are built once in GitHub Actions, published to GitHub Container Registry, then pulled
and started on the server over SSH. Secrets never enter the images or the repository.

## Flow

1. CI goes green on `main` (contracts, Go, ML, frontend, Playwright E2E).
2. `build` pushes three images to GHCR:
   `ghcr.io/<owner>/teamopt-backend`, `-ml`, `-frontend`, tagged `sha-<7>` (plus `latest` on `main`).
3. `deploy` copies `deploy/prod/docker-compose.yml` and `deploy/nginx/nginx.conf` to the server,
   writes `.env` from repository secrets/vars, pulls the images, migrates/seeds, restarts the stack
   and verifies `/api/v1/healthz`, `/ml/healthz` and `/` through the gateway.
4. If verification fails, the previous tag recorded in `.env` is restored and the stack is restarted.

## Server prerequisites

- Linux host with Docker Engine and Compose v2 (`docker compose version`);
- password-based SSH access for the deploy user; the user must be able to run `docker`
  (`PasswordAuthentication yes` must be enabled in the server's `sshd_config`);
- a writable deployment directory (default `/srv/teamopt`) with enough space for images and `pgdata`;
- inbound access to the gateway port (default `80`) and outbound HTTPS to `ghcr.io`.

The directory layout created on the server:

```text
<DEPLOY_PATH>/
├── .env                    # generated by CD, chmod 600 recommended
├── prod/docker-compose.yml # copied by CD from deploy/prod/
└── nginx/nginx.conf        # copied by CD from deploy/nginx/
```

Only the gateway publishes a host port. PostgreSQL, backend, ML and frontend stay on the internal
Compose network; their data lives in the named `pgdata` volume.

## Repository settings

Settings → Secrets and variables → Actions. Placeholders in this document are examples; use
synthetic accounts only (privacy rule: no names, salaries or real personal data).

### Variables

| Variable | Example | Purpose |
| --- | --- | --- |
| `DEPLOY_HOST` | `192.0.2.10` | SSH host of the server |
| `DEPLOY_USER` | `deploy` | SSH user |
| `DEPLOY_PATH` | `/srv/teamopt` | Deployment directory |
| `DEPLOY_SSH_PORT` | `22` | SSH port (optional) |
| `GATEWAY_PORT` | `80` | Host port for the nginx gateway |
| `POSTGRES_USER` | `teamopt` | Database user |
| `POSTGRES_DB` | `teamopt` | Database name |
| `AUTH_TOKEN_TTL_MINUTES` | `60` | JWT lifetime |
| `GHCR_USER` | `morozzz7` | Registry user for the optional PAT login (defaults to the actor) |
| `LLM_BASE_URL` | *(empty)* | Override the OpenAI-compatible endpoint on the server |
| `LLM_MODEL` | `deepseek-flash` | Model name supported by that endpoint (`deepseek-v4-pro` is the other known option); unset or blank falls back to `qwen/qwen-2.5-72b-instruct`, which fails on providers that do not serve it |

### Secrets

| Secret | Purpose |
| --- | --- |
| `DEPLOY_SSH_PASSWORD` | SSH password for `DEPLOY_USER` |
| `POSTGRES_PASSWORD` | Database password |
| `AUTH_JWT_SECRET` | HS256 signing key; must be long and unique per environment |
| `AUTH_USERS` | JSON array of synthetic accounts, e.g. `[{"login":"manager","password":"demo","actor":"emp_mgr01"}]` |
| `LLM_API_KEY` | Optional key for brief extraction (leave empty to run deterministic paths only) |
| `GHCR_PAT` | Optional token with `read:packages` when the GHCR packages are private |

GHCR packages inherit the repository visibility. If the packages are private, either grant the
server access once (`printf '%s' "$PAT" | docker login ghcr.io -u <user> --password-stdin`) or set
`GHCR_PAT`, which makes CD log in on every deployment.

Create a `production` environment in Settings → Environments if you want required reviewers before
deploying; the workflow references it, so protection rules are respected automatically.

## Manual deploy and rollback

```bash
cd /srv/teamopt
compose="docker compose -f prod/docker-compose.yml --env-file .env -p teamopt-prod"

$compose pull
$compose up -d --wait postgres
$compose run --rm --entrypoint /usr/local/bin/seed backend   # migrations + reference data
$compose up -d --remove-orphans --wait --wait-timeout 120

curl -fsS http://127.0.0.1/api/v1/healthz
curl -fsS http://127.0.0.1/api/v1/readyz
curl -fsS http://127.0.0.1/ml/healthz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1/
```

To roll back, change `IMAGE_TAG` in `.env` to a previously published `sha-<7>` tag and rerun the
commands above. Database migrations are additive; rolling back application code does not roll back
already applied migrations.

A manual redeploy without rebuilding is available through **Actions → CD → Run workflow**: set
`existing_tag` to a published tag (for example `sha-3975927`) or leave it empty to build from `ref`.

## Operations

```bash
$compose ps                 # service health
$compose logs -f backend ml # follow service logs
$compose exec postgres psql -U teamopt -d teamopt -c '\dt'  # inspect schema
```

Keep `.env` outside git and restrict it to the deploy user (`chmod 600 .env`). The application uses
synthetic employee ids (`emp_*`) and grade coefficients; no personal data or salaries are stored.
